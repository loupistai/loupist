# Schedule

Schedule runs two kinds of tasks. Each Loupist has one built-in morning briefing and, separately, one evening briefing about what it follows. Each edition's days and time can be changed. The evening one covers the trading day that is ending and what is due next; turning one edition on or off leaves the other. Custom tasks, including alerts, are defined in Bot. When Schedule is empty, its setup cards share the same reading width as the Bot greeting and stack on narrow windows. **Turn on** enables the weekday briefing or the filings and results watch directly from its card. **Ask Bot** opens the home chat with an editable example. A short charge notice appears below the setup cards, under the list header while a briefing can be enabled, and beside confirmation for proposed runs. Scheduled work can run while Loupist is open or in the menu bar. The briefing carries a **Built in** badge in its list row and detail. That badge is the only "built in" label; the row does not repeat it as a sentence. Once any task exists, each briefing edition always has its own row in the list, under Briefings, in Active and All: while it is on (or waiting for an OK) it is the ordinary task row; while it is off (never turned on, or turned off) the row shows its name, the Built in tag and what it does in one line, with **Off** beside **Turn on** at the row's end, centred together on the row; Turn on enables it directly, and the header's task count leaves it out. A briefing that was turned off keeps its task, so its name still opens the detail with its runs (`schedule-briefing-off`).

Bot’s More menu opens task history. The page has one h1, the app's location heading "Schedule" (예약), named as the page header and the sidebar row are; it takes focus when Bot's Scheduled tasks opens the page. Active and All filters, task details, run readers, linked evidence and notifications use the same saved task and run IDs. Focusing a control below the fold in a run scrolls it into the reader. A run's answer renders as the same card as in Chat, inside the run's own execution scope: its citations, links and workspace files open beside the briefing's own chat, which the Chat tab shows first (`useAppOpen`'s `openIn`), and a conflict card offers Show in World. A briefing's reader shows what changed in World, the followed assets it read (by the names they were followed by) and Looking ahead (due Journal checks, the next run and skipped tools); it carries no asset deltas, results or alerts. A task's detail names the model the host resolves for the next run and offers Pause or Resume (Turn on for a proposed task), Run now and, for a custom task, Delete after a confirmation that says its run history and the run sessions the user never wrote in go with it, while sessions the user wrote in stay in Research sessions and what it saved to Memory stays; these call `scheduled_task_set_status`, `scheduled_task_run_now` and `scheduled_task_delete` directly, so stopping a recurring model run never needs a model call. The briefing is turned off rather than deleted and a completed one-time task cannot be resumed. A failed last run says why beside those controls. A run is worded by its task's kind: a briefing's run is a briefing ("Couldn't finish this briefing", "Preparing your briefing…"), any other task's is scheduled research ("Couldn't finish this scheduled research", "Running this research…"). A failure with no known reason is said by that title alone, with its Details. A failed run's reader says why and offers Run now, which runs its task once more (`scheduled_task_run_now`) and shows the task, where the new run appears; reloading would only show the same failure, so Try again is kept for a reader that could not load. A custom task's prompt sits under a Prompt (요청 내용) label, and is left out when it only repeats the title. The Active and All filter appears once a task exists. Bot can change the built-in briefing’s days and time or a custom task’s time or prompt. The detail’s Change in Bot action drafts the request in the composer. The list footer’s Ask Bot action opens Bot with its composer focused; it follows the last row as another row would, after a hairline. The header, list and task detail share one centred column, as wide as Following's (the chat column inside 32 px gutters). A clear request registers immediately and returns the cadence and next execution time. A research session hands the request to its own Bot and stays open.

The delete confirmation also explains that summaries already delivered to Bot
stay there without a link to the run. A long task name in a session header or
Bot result can shorten with an ellipsis while the date stays visible. The
tooltip carries the full label.

A task with a check shows its one-line `when_met_summary` as "When it is met",
Reads, recent check evaluations and its versions in the detail. The run's
instructions sit behind Show instructions. Arguments are label and value rows;
`asset_ids` show the assets' names, and an id that is no longer there reads
Removed asset. View code toggles to Hide code. The dry run lists each day the
check would have been met, with that date and the reading it returned. In the
detail the task is called a check and tells you when the check is met. Check
history includes checks that started no run. Turn on, Test now, View code and
Go back call the trigger bridge commands. The code and buttons use the full
card width. The asset page's Price moves switch proposes the bundled
price-band check. It runs after the user turns that version on. That row says
no model runs until the check is met. A model-run preset keeps the line that a
check may incur AI charges.

The scheduler runs briefings and custom tasks. An alert is a custom task whose prompt states the condition and evidence to check. A successful check that finds nothing to report can call `schedule_quiet` to keep its run in history without a Bot post or inbox entry; the task's Runs list marks it "Nothing to report" (보고할 내용 없음) beside its time, with its summary, and never as unread.

Schedule lists each task’s runs, newest first. Bot posts a dated copy of each delivered result. Open on the post leads to the same run reader as Schedule. The Schedule row counts unread results for the selected Loupist. While a run is in progress, including one started with Run now, a spinner takes the count’s place. The row’s tooltip and accessible name give the task title or the number of concurrent runs. In the collapsed sidebar, the spinner appears at 8 px in the icon’s corner. The latest unread count returns when the last run ends. Seeing a Bot delivery or its run reader for one second marks it read. Quiet successful runs never count.

Continue in Chat opens the run’s session. Sending a message there adds it to Research sessions and changes the reader’s action to Open the session. The reader checks that the session still exists before opening it. A continued session that began with a scheduled request has a clock in the sidebar. Its header links to the dated run for a fresh session, or to the task for a continuing session such as the briefing. If the task or the individual run was removed, the header retains its origin as text. A chat started by the user keeps its own header even if a schedule later posts to it. [Run retention](../runtime/scheduled-runs.md#scheduled-chats).

The run reader centers its answer at the chat reading width. The header identifies the author and start time once.

With an active task, Schedule offers **Open at login** above the list if the installed Mac app can register and login is off. Choosing it enables menu-bar residence and confirms the change for this visit. Closing the hint dismisses it across all Loupists and restarts. Once login has been enabled the hint stays dismissed, including after login is turned off again.


## Watches

Watches are scheduled checks with a condition for reporting. Schedule lists four sections, in order: Briefings (a briefing that is off stays here), Checks (a task with a trigger), Scheduled research (watches and other custom tasks), and Learning (a task of kind `learning`, once one exists). A learning program made from a bundled preset (`program.preset`: Track daily, Theme, Company filings, Economic series, Question, Market) names it in its Bot card's kicker ("Learning program · Market") and as Template in its Schedule detail; an id this build does not know is not shown. A turn-on refused at the Loupist's cap says that cap ("Up to 7 programs can be active."), read from the host's refusal. Empty sections stay hidden, except Briefings. Each heading shows how many rows it contains, under Active and under All. The header "{n} tasks · {time zone}" adds a line when today's background allowance is at least 80 percent used, and says it is waiting for tomorrow's allowance when that allowance is used up. A task held for the allowance, the AI plan limit, or credit says why. Run now asks before it starts a held task, and opens that same confirmation when the host refuses the click with `ask_first` because the allowance ran out before a hold was stored. A check's detail shows its terms, cadence, reporting rule and notification policy. **Notifies** changes delivery directly. **Now** alerts after a result, **Digest** collects results for the next briefing, and **In Bot only** keeps results in the conversation. A task whose delivery is `briefing` is not posted in Bot; the next briefing receives it as a background run. A recurring preset starts with a check as soon as it is turned on. A results follow-up starts the morning after the specified results date. Bot may give it `event_date` (a day, `exact` when announced, `estimated` when only expected); the task then carries `event {date, precision}`, older tasks have none, and `results_date`, when also given, must name the same day.

A learning row shows its title, up to three subject chips (then a count; an asset chip opens that asset), its cadence and next run, and the last outcome. It says it is waiting for another learning run when the app-wide learning slot is occupied. Run now on a held learning program asks first, then sends that confirmation. The same confirmation opens when the host's refusal is `ask_first` and the program has no stored hold yet. The program detail shows the brief (six lines, then Show all), what it is about, when it runs, its depth, sources, what it keeps, how it reports, where it delivers, its request budget, and the model. Runs are newest first. Run now, Pause or Resume, Delete (after confirmation), and Ask Bot to change act on the program. Ask Bot to change drafts the request in the composer. A learning run says how many requests it used and, when the budget outcome is refused or cancelled, that it stopped at its request limit. It lists what that run's answer learned, by the run's message. Undo restores the sections that run filed and says how many sections changed since and were kept. Those counts are stored with the undo marker and returned on the run, so opening it again shows the same kept count and not the button. A learning program proposed in chat is a card in the schedule-card family: Turn on confirms it, and Not now declines it for the visit.

Edit opens the program editor (`LearningProgramEditor`): title, What to learn (at most 8 KB, counted as the host counts it), About (up to eight subjects: followed assets, World names, Lens pages or plain names), When (every day, chosen days or every few hours, in the schedule's own time zone; a one-time program keeps its time unless switched), Depth, Sources (every enabled connection or the ones already chosen, and web research), Keeps, Reports and Delivers. Save is the default action and stays off until a field changes; it sends only the changed fields with the revision the editor opened on through `learning_program_update`, which validates them as `learning_program_save` does. A direct edit needs no proposal, and a run in progress keeps what it started with. The patch carries `depth`, `sources` and `keeps` as their own fields. A refusal is `invalid_request` with `{field, reason}`: the editor shows its own line under that field and keeps the host's English `reason` out of the view; a stale revision says "This program changed. Reload". A paused program, or one without an AI account, stays editable and says why it will not run. Escape and Cancel close at once when nothing changed and ask before discarding changes. Undo all runs first asks the host for the counts with a dry `learning_program_undo_all` and states them (runs, sections restored, sections kept because they changed since); confirming undoes every run newest first in one transaction and leaves "Undid {n} runs ({k} sections changed since and were kept)". Sources stay, and a thesis move keeps its own Undo. A Lens section whose newest op a learning run filed, with nothing changed since, carries "Learned {date} · {program}" in the page reader, which opens that run here; a method's Lens learning panel says in one line why method learning waits (`knowledge_learning_state`). The host side is in [Editing, Undo all and learned marks](../knowledge/learning.md#editing-undo-all-and-learned-marks).
