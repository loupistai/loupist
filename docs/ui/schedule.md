# Schedule

Schedule runs two kinds of tasks. Each Loupist has one built-in morning briefing about changes to followed assets. Its days and time can be changed. Custom tasks, including alerts, are defined in Bot. When Schedule is empty, two cards share the same reading width as the Bot greeting and stack on narrow windows. **Turn on** enables the weekday briefing directly. **Ask Bot** opens the home chat with an editable example. The note below the cards explains AI account use and when scheduled work can run. Once a task exists, the note moves under the list header. The briefing carries a **Built in** tag in its list row and detail. Once any task exists, the briefing always has its own row in the list, under Active and All: while it is on (or waiting for an OK) it is the ordinary task row; while it is off (never turned on, or turned off) the row shows its name, the Built in tag, what it does in one line, **Off** and **Turn on**, which enables it directly, and the header's task count leaves it out. A briefing that was turned off keeps its task, so its name still opens the detail with its runs (`schedule-briefing-off`).

Bot’s More menu opens task history. The page has one h1, the app's location heading "Schedule" (예약), named as the page header and the sidebar row are; it takes focus when Bot's Scheduled tasks opens the page. Active and All filters, task details, run readers, linked evidence and notifications use the same saved task and run IDs. Focusing a control below the fold in a run scrolls it into the reader. A run's answer renders as the same card as in Chat, inside the run's own execution scope: its citations, links and workspace files open beside the briefing's own chat, which the Chat tab shows first (`useAppOpen`'s `openIn`), and a conflict card offers Show in World. A briefing's reader shows what changed in World, the followed assets it read (by the names they were followed by) and Looking ahead (due Journal checks, the next run and skipped tools); it carries no asset deltas, results or alerts. A task's detail names the model the host resolves for the next run and offers Pause or Resume (Turn on for a proposed task), Run now and, for a custom task, Delete after a confirmation that says its run history and the run sessions the user never wrote in go with it, while sessions the user wrote in stay in Research sessions and what it saved to Memory stays; these call `scheduled_task_set_status`, `scheduled_task_run_now` and `scheduled_task_delete` directly, so stopping a recurring model run never needs a model call. The briefing is turned off rather than deleted and a completed one-time task cannot be resumed. A failed last run says why beside those controls. A run is worded by its task's kind: a briefing's run is a briefing ("Couldn't finish this briefing", "Preparing your briefing…"), any other task's is scheduled research ("Couldn't finish this scheduled research", "Running this research…"). A failure with no known reason is said by that title alone, with its Details. A failed run's reader says why and offers Run now, which runs its task once more (`scheduled_task_run_now`) and shows the task, where the new run appears; reloading would only show the same failure, so Try again is kept for a reader that could not load. A custom task's prompt sits under a Prompt (요청 내용) label, and is left out when it only repeats the title. The Active and All filter appears once a task exists. Bot can change the built-in briefing’s days and time or a custom task’s time or prompt. Each detail names the available changes. Its Ask Bot link drafts the request in the composer when the shell provides one. The list's footer ("tell Bot what you want and when") has the same link, which opens Bot with its composer focused. A clear request registers immediately and returns the cadence and next execution time. A research session hands the request to its own Bot and stays open.

The delete confirmation also explains that summaries already delivered to Bot
stay there without a link to the run. A long task name in a session header or
Bot result can shorten with an ellipsis while the date stays visible. The
tooltip carries the full label.

The scheduler runs briefings and custom tasks. An alert is a custom task whose prompt states the condition and evidence to check. A successful check that finds nothing to report can call `schedule_quiet` to keep its run in history without a Bot post or inbox entry; the task's Runs list marks it "Nothing to report" (보고할 내용 없음) beside its time, with its summary, and never as unread.

Schedule lists each task’s runs, newest first. Bot posts a dated copy of each delivered result. Open on the post leads to the same run reader as Schedule. The Schedule row counts unread results for the selected Loupist. While a run is in progress, including one started with Run now, a spinner takes the count’s place. The row’s tooltip and accessible name give the task title or the number of concurrent runs. In the collapsed sidebar, the spinner appears at 8 px in the icon’s corner. The latest unread count returns when the last run ends. Seeing a Bot delivery or its run reader for one second marks it read. Quiet successful runs never count.

Continue in Chat opens the run’s session. Sending a message there adds it to Research sessions and changes the reader’s action to Open the session. The reader checks that the session still exists before opening it. A continued session that began with a scheduled request has a clock in the sidebar. Its header links to the dated run for a fresh session, or to the task for a continuing session such as the briefing. If the task or the individual run was removed, the header retains its origin as text. A chat started by the user keeps its own header even if a schedule later posts to it. [Run retention](../runtime/scheduled-runs.md#scheduled-chats).

The run reader centers its answer at the chat reading width. The header identifies the author and start time once.

With an active task, Schedule offers **Open at login** above the list if the installed Mac app can register and login is off. Choosing it enables menu-bar residence and confirms the change for this visit. Closing the hint dismisses it across all Loupists and restarts. Once login has been enabled the hint stays dismissed, including after login is turned off again.
