1. **P2 — The new method-write gate still permits removing safeguards without user teaching.** `apps/loupist/src-tauri/src/commands/tool_executor/lens_file.rs:263–270` tests only `LensOp::Put`. After an exact method read, a research turn can submit `retire` for its `limits` section, with the returned digest, and no `said` reference. The normal writer removes the section (`knowledge/lens_page.rs:876–886`); neither that writer nor the retire resolver checks user authorization. A `summary` operation can likewise broaden the method's advertised scope without a put. This also works in an unattended run, even though such a run cannot supply `said`. Thus a one-company research turn can erase the existing exception instead of replacing it, bypassing the safeguard this change is meant to establish. **Suggested fix:** enforce the method-authority rule for every substantive turn mutation, including retirement and summary changes. Give those operations a way to carry the current user's authorization, or reject them when it is absent; keep direct user edits and the separately validated learning path available. Add negative interactive/unattended retire and summary cases, plus a positive user-requested deletion. This is a traced executable path, not a claimed live-model observation.

2. **P2 — Omitting `about` still turns the same company's research into independent cases.** `apps/loupist/src-tauri/src/knowledge/learning.rs:471–485` assigns an unanchored page the identity `page:<id>`, and `:315–316` treats disjoint sets as different cases. Chat A can file a company subject page against its annual report; Chat B can file an idea such as “Utilization recovery thesis” about the same company against a different report, omitting the optional `about`. They pass both independence checks. Two unanchored ideas, or two unresolved aliases of the same company, also pass. This is an ordinary tool shape: `agent/tool-catalog.json:1003` describes `about` specifically as what a *subject* page is about. The new test even expects an unanchored idea with the same ramp text to start a review (`knowledge/learning/tests.rs:1258–1262`). Publication repeats the same identity check, so an overgeneralizing model output is not rejected there. **Suggested fix:** distinguish unknown case identity from independently identified cases; do not use an arbitrary page ID as evidence of a different company. Normalize/resolve subject identity for eligible subject and idea pages, advertise `about` for both, and defer ambiguous same-company candidates. Add a subject-plus-unanchored-idea control and unresolved-name/alias controls. The documented exception accurately describes the implementation, but leaves the earlier same-company finding open.

3. **P2 — HV-003 passes even when the saved safeguard is reversed.** `apps/loupist/evals/agent/heldout/lens-behavior-heldout-v1.json:243–265` checks one method, a section containing `REIT|master limited`, and the answer's DCF reasoning. It never checks that the method stayed unchanged or still prohibits earnings-cover use for those entities. I ran the real deterministic grader with a single stored method whose new limit says “Apply earnings-cover rules to REITs and master limited partnerships without exception”: both page assertions passed. A correct DCF answer still satisfies the sole rubric. Because this session is `role: probe` (`:231`), `judgeItems` does not add the generic train-session save-precision judgment either. **Suggested fix:** assert that the seeded method has no operations or unchanged content, while allowing legitimate subject-page filings, and add a semantic saved-page rubric preserving the actual exclusion and fallback. Include the reversed/negated safeguard as a grader counterexample. This case currently tests answer restraint, but cannot establish its title's promise that the method is left as it was.

4. **P2 — HV-006 measures a title match, not retrieval of the adopted method.** `apps/loupist/evals/agent/heldout/lens-behavior-heldout-v1.json:552–554` requires an English title regex, although the creation step at `:523–528` allows any method title. In the actual grader, an exact read of a correct method named “Supplier-financed growth check” fails. Conversely, an exact read of a **subject** page named “Halden working capital” passes: `grade.mjs:348–356` excludes source/note/journal/world reads but does not require a method or the created record ID. The answer rubric can then be met from the probe's inventory/payable figures without using the adopted method. **Suggested fix:** bind the later assertion to the method record created in the adoption turn and verify exact-read/application of that record, independently of its title and language. Add both counterexamples. This avoids both false failures of useful methods and false evidence of transfer.

5. **P3 — A shared historical name can override two distinct resolved company IDs.** `apps/loupist/src-tauri/src/knowledge/learning.rs:476–479` inserts both `node:<id>` and `name:<fold>` even for resolved anchors. For example, an idea created when “Atlas” resolved to company A retains `(A, atlas)`; after World disambiguates/renames A and a different company B owns that name, a second idea can have `(B, atlas)`. Name-based creation retains the name (`knowledge/lens.rs:394–406`), and anchor resolution only updates pending anchors (`:1093–1107`), so the older resolved anchor remains validly bound to A. These two different companies then fail `is_disjoint` because of `name:atlas`, preventing a useful review. **Suggested fix:** make a resolved node authoritative; compare qualified names only for genuinely unresolved identities, resolving pending names against the same current identity index when possible. Test distinct resolved nodes with a colliding historical name, as well as a pending and resolved spelling of the same node. This is identity conflation for learning, not a claim that this code physically merges Lens pages.
